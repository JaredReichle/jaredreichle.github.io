About

I work with teams that test complex systems on real hardware. The job usually starts with a pile of manual steps that only a couple of people fully understand. I turn that into automation the whole team can run and trust.

Recently I built a message set generator module that takes released message definitions and translates them into message classes that can be used as runtime objects in multiple languages, all for use in different testing tools.

I started in electrical engineering. Then I started writing small scripts to cut repetitive lab work. One script became five, and five became tools people used every day. Somewhere in there I realized I liked building software more than drawing schematics.

The hardware background still matters daily. When a test rig misbehaves, I don't stop at the logs. I trace the signal, question my assumptions, and compare what the device does with what the code expects. If you've chased a bug across three systems, you know how blame bounces around. Knowing both sides makes it easier to find what's actually wrong.

I'm finishing an M.S. in Computer Science at Georgia Tech, specializing in AI. I'm using the coursework and applying it directly in the tooling I develop. For example, I've been configuring a local language model for a chat bot that can semantically map a user's request to an actual test action or some other requested resource (i.e. "Give me the latest audit report for this test line").
